# النشر على Vercel — الدليل العملي

هذا الدليل يشرح ما تحقّق فعلاً من الخطة المقترحة، وما يحتاج تعديلاً قبل أن تعمل على Vercel، ثم خطوات النشر.

## ١. ما صحّ في الخطة

| البند | الحالة |
| --- | --- |
| Vercel Blob: 1 GB تخزين شهرياً في Hobby | ✔ مطابق لصفحة الأسعار |
| 10 GB نقل بيانات Blob شهرياً | ✔ مع عمليات: 10,000 بسيطة و2,000 متقدمة |
| حد الملف الواحد 5 TB والرفع المجزّأ فوق 100 MB | ✔ عبر `multipart: true` في SDK |
| Next.js على Vercel | ✔ (Next 16، App Router) |

## ٢. أربع تصحيحات ضرورية

### أ. الرفع لا يمكن أن يمرّ عبر دالة Vercel

سقف جسم الدالة **4.5 MB**؛ أي رفع عبر الخادم يفشل عند 413. لذلك:

- المتصفح يطلب **جلسة رفع** من `/api/uploads` (تحقّق مسارات + أحجام + حصّة + حدّ معدّل)،
- ثم يرفع الملفات **مباشرة** إلى Blob عبر `upload()` من `@vercel/blob/client` باستخدام توكن قصير العمر يصدره `/api/blob/upload` عبر `handleUpload`،
- ثم `/api/uploads/<id>/commit` يقرأ ما وصل فعلاً ويثبّت الإصدار.

التوكن مقيّد بمسار واحد: `sites/<site>/<version>/<المسار>` — لا يمكن إعادة استخدامه للكتابة فوق ملفات شخص آخر.

الحد الافتراضي للملف الواحد في الكود 100 MB (`ERFA3LY_MAX_FILE_BYTES`). رفعه إلى 5 TB ممكن تقنياً، لكن الروابط التي لا يستطيع أحد فتحها ليست ميزة؛ ارفعه بوعي.

### ب. المعاينة تُقدَّم من دالتك، لا من رابط Blob

لو أرسلنا المستخدم إلى رابط Blob العام لضاعت ترويسة العزل:

```
Content-Security-Policy: sandbox allow-scripts allow-forms …
```

لذلك كل شيء يُقدَّم من `/api/raw/<site>/<version>/<path>`:

- HTML: عبر الدالة، مع حقن shim للتخزين المحلي — صغيرة دائماً تقريباً.
- الأصول الثابتة (صور، خطوط): عبر الدالة أيضاً، لكن بذاكرة تخزين طويلة لأن مسار الإصدار ثابت (`immutable`).
- لو أردت تقليل استدعاءات الدوال: أضف مساراً يعيد `redirect` إلى رابط Blob للأصول غير HTML فقط. الثمن: تفقد الترويسة على تلك الأصول، وهي على نطاق Blob منفصل لا يحمل كوكيز المنصة.

### ج. تشغيل ZIP لا يعني نشر التطبيق

فك الضغط في هذا المشروع:

1. يفحص الأحجام **المعلنة** قبل فكّ الضغط (`fflate` + `filter`) → لا قنابل ZIP،
2. يرفض `..` والمسارات المطلقة (zip-slip) قبل أن يلمس أي شيء،
3. لا يكتب على القرص إطلاقاً: يفكّ في الذاكرة ثم يكتب عبر واجهة التخزين،
4. يستنتج نقطة الدخول: `index.html` في الجذر، أو داخل مجلد واحد يغلّف الموقع (وهو ما ينتجه `zip -r`)، أو صفحة HTML وحيدة، أو مستند وحيد،
5. يفحص علامات التطبيق (`package.json` بسكربتات، `server.js`، `requirements.txt`، `Dockerfile`…) ويعرض تحذيراً واضحاً: «يحتاج خادماً».

ما لا يفعله ولن يفعله: `npm install`، تنفيذ أوامر بناء، تشغيل خادم، توصيل قاعدة بيانات. المشاريع التي تحتاج Backend تحتاج بيئة تشغيل منفصلة (Vercel Functions أخرى، Fly.io، Railway…).

سقف فكّ الضغط في الدالة 200 MB ومنطقة الذاكرة 1 GB (`vercel.json`). للمواقع الأكبر: ارفع المجلد مباشرة (مسار الأصول المتعددة) بدل ZIP.

### د. لا عمليات طويلة العمر ولا مؤقتات داخل العملية

- **الرفع المجزّأ إلى Blob** هو الحل الصحيح للملفات الكبيرة، لا تقسيم عندنا.
- **الصيانة**: `vercel.json` يضيف Cron يومياً إلى `/api/cron/gc`، محمي بـ `CRON_SECRET` (يفشل مغلقاً إن لم يُضبط). ينظّف جلسات الرفع المتروكة والمواقع المحذوفة بعد مدة الاحتفاظ.
- **حدّ المعدّل** في قاعدة البيانات لا في ذاكرة العملية (كل نسخة لها ذاكرتها على Vercel).
- **بيانات الاعتماد**: لا كوكيز جلسة للمنصة تُقرأ من داخل الإطار المعزول.

## ٣. الحدود والأرقام قبل أن تنشر

| البند | Hobby | المعنى العملي |
| --- | --- | --- |
| تخزين Blob | 1 GB | نسخة تجريبية/فريق صغير، لا أرشيفاً |
| نقل Blob | 10 GB/شهر | موقع 500 MB = عشرون مشاهدة فقط |
| استدعاءات الدوال | 1M/شهر | كل صفحة معاينة = استدعاء، والأصول كذلك |
| مدة الدالة | 10s (Hobby) | فكّ ZIP كبير يحتاج Pro أو رفع مجلد |

لذلك: `ERFA3LY_QUOTA_BYTES` الافتراضي 900 MB يترك هامشاً داخل الـ 1 GB. للحجم الجدّي: خطة Pro، أو مشغّل S3/R2 (الواجهة `Storage` جاهزة لإضافته في ملف واحد)، لأن نقل Blob على Hobby يتوقف عند تجاوز الحد.

## ٤. خطوات النشر

```bash
# 1) المستودع
git push origin main            # أو اربط المستودع من لوحة Vercel

# 2) من لوحة Vercel
#    Storage → Create → Blob  (يضيف BLOB_READ_WRITE_TOKEN تلقائياً)
#    Storage → Create → Postgres (Neon)  ← يعطيك DATABASE_URL
#    Settings → Environment Variables:
#      ERFA3LY_QUOTA_BYTES=943718400
#      ERFA3LY_MAX_FILE_BYTES=104857600
#      ERFA3LY_MAX_VERSION_BYTES=524288000
#      CRON_SECRET=<سلسلة عشوائية طويلة>
#      ERFA3LY_PUBLIC_URL=https://<نطاقك>

# 3) محلياً، للتحقق
npm ci
npm run build
npm start
```

نقاط يجب الانتباه لها:

- **لا تضع `ERFA3LY_DATA_DIR` على Vercel**: لا قرص دائم. الكود يرفض التشغيل هناك بدون `DATABASE_URL` و`BLOB_READ_WRITE_TOKEN` برسالة واضحة (انظر `assertUsableRuntime`).
- **`BLOB_READ_WRITE_TOKEN` شرط لاختيار مشغّل Blob**؛ بدونه يذهب التطبيق إلى القرص المحلي، وهذا مستحيل على Vercel.
- **`CRON_SECRET`**: بدونه يعيد `/api/cron/gc` الرمز 503، أي أن الحذف النهائي لا يحدث. اضبطه.
- **النطاق**: `ERFA3LY_PUBLIC_URL` يستخدم في فحص `Origin` للطلبات المُصادقة بالكوكي وفي بناء الروابط المطلقة.
- **المعاينة على نطاق فرعي منفصل** (اختياري لكن مستحسن): اربط `preview.<domain>` كـ Domain وأضف `ERFA3LY_ALLOWED_ORIGINS`، ثم أضف `frame-src` مناسباً. العزل الحالي (CSP sandbox + iframe بلا `allow-same-origin`) يكفي، لكن نطاق منفصل يجعل التصيّد بالاسم مستحيلاً حتى نظرياً.
- **حجم الذاكرة** لمسار الـ commit مضبوط على 1024 MB في `vercel.json`؛ خفّضه إن رفعت حدود ZIP.

## ٥. التشغيل محلياً بدون أي خدمة

```bash
npm install
cp .env.example .env      # كل القيم فارغة
npm run dev               # http://localhost:3000
```

- التخزين: `./.erfa3ly-data/blobs`
- قاعدة البيانات: PGlite داخل `./.erfa3ly-data/pgdata` بنفس SQL الإنتاج
- المسار المباشر للرفع يعمل (بثّ إلى القرص) لأن مشغّل التخزين محلي
- الاختبارات: `npm test` (24 اختباراً: مسارات، ZIP، استنتاج نقطة الدخول)

## ٦. ما لم يُنفَّذ بعد (خطوات تالية واضحة)

- مصادقة حقيقية (OIDC) بدل كوكي المساحة المجهولة — ملف واحد (`src/lib/auth.ts`).
- روابط مشاركة بكلمة مرور وصلاحية تعديل/تعليق.
- مشغّل S3/R2 إضافي بديل عن Blob (نفس الواجهة `Storage`).
- معاينة Office (يحتاج Gotenberg خارج Vercel: خدمة منفصلة).
- بحث نصي كامل داخل المستندات (استخراج نص PDF).
- نقل الأصول الثقيلة إلى نطاق معاينة منفصل مع ترويسات عزل مكافئة.

## ٧. استكشاف الأعطال

### لا يوجد `BLOB_READ_WRITE_TOKEN` لكن المتجر مربوط

هذا طبيعي في نمط الربط الأحدث: Vercel يحقن **`BLOB_STORE_ID`** (وقد ترى أيضاً
`BLOB_WEBHOOK_PUBLIC_KEY`) ويعطيك في كل تشغيل توكن OIDC قصير العمر
(`VERCEL_OIDC_TOKEN`). النسخة الحالية تدعم الوضعين:

| ما يوجد في البيئة | المصادقة | رفع المتصفح |
| --- | --- | --- |
| `BLOB_READ_WRITE_TOKEN` | توكن دائم | `upload()` → `/api/blob/upload` |
| `BLOB_STORE_ID` فقط (على Vercel) | OIDC مؤقت | `uploadPresigned()` → `/api/blob/upload-presigned` |

لا تحتاج إلى توليد توكن يدوياً. المطلوب فقط **إعادة نشر (Redeploy)** بعد ربط المتجر،
لأن متغيرات البيئة تُقرأ عند البناء/التشغيل. تحقّق بـ `/api/health`:

```json
{ "storage": "blob", "blobAuth": "oidc", "blobStoreIdPresent": true, "problems": [] }
```

إن ظهر `"blobAuth": "none"` مع `"blobStoreIdPresent": true` فالربط لم يُطبَّق على هذا
النشر بعد — أعد النشر؛ وإن استمر، أضف `BLOB_READ_WRITE_TOKEN` من صفحة المتجر
(Store → `.env` / Connect Project).

### `413 FUNCTION_PAYLOAD_TOO_LARGE` عند رفع الملفات

هذا يعني أن المتصفح رفع إلى `/api/uploads/<id>/files` — أي أن الخادم أعاد `driver: "local"`، أي أن **`BLOB_READ_WRITE_TOKEN` غير موجود في بيئة النشر**. على Vercel لا قرص دائم، وسقف جسم الدالة 4.5 MB، لذلك رفض Vercel الطلب بعد أن أرسل المتصفح كامل الملف.

الحل:

1. Vercel → **Storage → Create → Blob** ثم اربطه بالمشروع (يضيف المتغير تلقائياً).
2. تأكد من ظهوره في **Settings → Environment Variables** لبيئة **Production**.
3. **Deployments → ⋯ → Redeploy** — إضافة متغير لا تؤثر على نشر قائم.

النسخة الحالية لا تنتظر حدوث 413: `/api/uploads` يعيد **503** مع قائمة النواقص قبل أن يبدأ الرفع، والواجهة تعرض شريط «الرفع معطّل حتى يكتمل الإعداد» وتعطّل أزرار الرفع.

### شريط «إعداد النشر ناقص» في الصفحة

اقرأ الرسالة نفسها؛ تذكر اسم المتغير المفقود بدقة (`BLOB_READ_WRITE_TOKEN` أو `DATABASE_URL`/`POSTGRES_URL`).

### فحص سريع بعد النشر

```bash
curl -s https://<نطاقك>/api/health | jq
# {
#   "ok": true,
#   "vercel": true,
#   "storage": "blob",          ← لو ظهر "local" فتوكن Blob ناقص
#   "database": "postgres",     ← لو ظهر "missing" فرابط القاعدة ناقص
#   "databaseVariable": "DATABASE_URL",
#   "problems": []
# }
```

`503` من هذا المسار يعني أن النشر غير مكتمل الإعداد، والرسائل تشرح السبب. لا يعرض المسار أي قيمة سرية، فقط أسماء المتغيرات الموجودة.

### المعاينة فارغة أو بيضاء بينما الصفحة تعمل عند فتح الملف محلياً

سببان شائعان، ولوحة الموقع أصبحت تكتشفهما وتعرضهما فوق المعاينة:

1. **أصول لم تُرفع.** لو ظهر «ملفات مفقودة داخل هذا الإصدار» فالصفحة تشير إلى
   `assets/css/style.css` وأمثاله ولا يوجد في الإصدار إلا ملف HTML واحد. ارفع المجلد
   كاملاً أو ZIP (مع `index.html` في الجذر)؛ الاستنتاج يتولّى تجريد المجلد الغلاف.
2. **واجهات ممنوعة في الأصل المعزول.** الصفحات التي تستخدم `localStorage` أو
   `indexedDB` أو `history.replaceState` تتوقف عند أول سطر داخل إطار معزول بلا
   `allow-same-origin`، فتبدو فارغة. هذه الواجهات `[LegacyUnforgeable]` على `window`
   ولا يمكن استبدالها بحقن سكربت. الحل الحقيقي: أصل منفصل للمعاينة.

#### إعداد أصل معاينة منفصل (مستحسن)

1. أضف نطاقاً فرعياً إلى نفس المشروع في Vercel (مثلاً `artifacts.example.com` أو نطاق
   `*.vercel.app` مخصص للمشروع).
2. اضبط `ERFA3LY_PREVIEW_ORIGIN=https://artifacts.example.com` و`ERFA3LY_PUBLIC_URL`
   على نطاق التطبيق، ثم أعد النشر.
3. النتيجة: المعاينة تُقدَّم من النطاق الفرعي بترويسة
   `Content-Security-Policy: frame-ancestors 'self' <app>` بدل `sandbox`، فيحصل الملف
   على أصل حقيقي (تخزين وتاريخ يعملان)، ويُضمَّن بـ `allow-same-origin`. العزل يبقى
   قائماً لأن كوكي المساحة host-only ولا يُرسل إلى النطاق الفرعي، والكود يرفض أي طلب
   مُصادق بالكوكي على نطاق المعاينة (`isPreviewRequest` في `src/lib/auth.ts`).

بدون هذا المتغير يظل العزل الافتراضي (أصل غامض) ويعرض الـ dashboard تنبيهاً بدل
معاينة صامتة.

### تحذير `SECURITY WARNING: The SSL modes 'prefer', 'require', and 'verify-ca'…`

هذا تحذير من `pg-connection-string` يظهر بجوار كل طلب، ولوحة Vercel تعرضه في مستوى
`error` فيبدو عطلاً — وهو ليس عطلاً. سببه أن `sslmode=require` في `DATABASE_URL` سيغيّر
معناه في pg v9.

النسخة الحالية تحسم TLS في مكان واحد (`src/lib/db-tls.ts`) وتزيل `sslmode` من الرابط
قبل تمريره إلى `pg`، فيختفي التحذير ولا يتغيّر السلوك:

| في الرابط أو البيئة | النتيجة |
| --- | --- |
| `sslmode=disable` / `allow` | بلا TLS |
| `sslmode=verify-full` / `verify-ca` | TLS مع التحقق من الشهادة |
| `sslmode=require` / `prefer` أو بلا `sslmode` | TLS بلا تحقق من الشهادة |
| مضيف loopback | بلا TLS |
| `ERFA3LY_DB_SSL=verify-full` | يفرض التحقق دائماً |

يعرض `/api/health` النمط الفعّال في `databaseTls`. إن كانت قاعدة البيانات بشهادة موقّعة
ذاتياً ولم تعمل الاتصالات، استخدم `ERFA3LY_DB_SSL=require`.

### أخطاء أخرى متوقعة

| الرسالة | السبب | الحل |
| --- | --- | --- |
| `unsafe relative path` / `blocked path segment` | ZIP يحتوي `..` أو `.git` أو `node_modules` | أعد ضغط المشروع دون مجلداته الداخلية |
| `the archive has no index.html…` | ZIP بلا صفحة دخول | ارفع مجلد البناء (`dist/`) أو أضف `index.html` |
| `zip rejected: entry too large` | ملف داخل ZIP يتجاوز `ERFA3LY_MAX_FILE_BYTES` | ارفع الملف وحده أو ارفع الحد |
| `quota exceeded` | تجاوزت مساحة المالك | احذف عملاً قديماً (تُفرَّغ المساحة بعد مدة الاحتفاظ) أو ارفع `ERFA3LY_QUOTA_BYTES` |
| `cross-origin write refused` | `Origin` لا يطابق النشر | اضبط `ERFA3LY_PUBLIC_URL` أو أضف الأصل في `ERFA3LY_ALLOWED_ORIGINS` |
| `503 CRON_SECRET is not configured` | مهمة التنظيف معطّلة | اضبط `CRON_SECRET` |
